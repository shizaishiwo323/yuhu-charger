# 复刻指南：给你常去的车棚也做一个

> 这份指南只讲**方法**，不包含具体的平台接口地址和参数。不同品牌的充电桩平台各不相同，
> 照着下面的思路自己观察一遍，一般一个晚上就能跑通。请只做**低频、只读**的查询，不要给平台添麻烦。

## 0. 你需要准备

- 一台电脑（Windows / macOS 都行），装好 Node.js 18+ 和 Python 3
- 电脑版微信（很多校园充电桩是“微信扫码 → 打开网页”）
- 一个 Cloudflare 账号（免费版就够：Worker 定时任务 + D1 数据库）
- 可选：一个自己的域名；没有也可以用 Cloudflare 自动分配的 `*.workers.dev` 地址

## 1. 去现场：拍二维码、画草图

1. 把车棚里**每一台主控器**上的扫码充电二维码都拍下来。用微信或任意扫码工具识别出链接，
   链接里通常带着这台设备的编号。玉湖 8 台的链接见 README。
2. 顺手画一张**现场草图**：每台主控器在哪、它的 12 个口沿着哪一排、编号从左到右还是从右到左、车头朝哪边。
   后面画大屏全靠这张图，这一步是“看得到真实布局”的关键。
3. 给每台主控器起个好记的名字（比如 Y1–Y8），和设备编号一一对应。

## 2. 抓包：找到“插座状态”是从哪来的

扫码充电的页面本质上是一个网页，它显示的“哪个口空闲”一定是向服务器请求来的。我们要做的就是找到这个请求。

1. 安装抓包工具，例如 [mitmproxy](https://mitmproxy.org/)：`pip install mitmproxy`（或 `uv tool install mitmproxy`）。
2. 启动代理，用 `--allow-hosts` **只拦截充电桩平台的域名**，其他网站的流量直接放行；
   再写一个几行的小插件，把请求和返回保存成 `jsonl` 文件方便事后看。
3. 把系统代理设置成 mitmproxy 的地址，用电脑版微信打开主控器链接（发到“文件传输助手”再点开最方便），
   点进“选择插座”页面。
4. 在记录里找：**哪个请求的返回里，有一段长度刚好等于插座数量的字符串或数组**？那个就是设备状态接口。
5. 对照页面上每个口的颜色和文字，推断每个状态码的含义（空闲 / 充电中 / 快充满时的浮充 / 故障……）。
   页面自己的 JS 里通常也有判断逻辑，可以直接看。
6. 用完记得**关掉系统代理**。

> ⚠️ 抓包记录里往往带有你自己的微信身份标识（比如 openId）。这些是你的个人信息，
> 甚至可能等同于“钱包钥匙”：**不要上传到任何公开的地方**，记得把记录文件写进 `.gitignore`。
> 监控“公共插座状态”一般用不到任何个人身份，能不带就不带。

先在本机用一个小脚本手动调用一次，确认能拿到和页面一致的结果，再继续。

## 3. 上云：每分钟巡查一次

为什么用 Cloudflare Worker？免费、不用自己维护服务器，自带定时任务和 SQLite 兼容的数据库 D1。

```bash
npm create cloudflare@latest my-charger   # 或者直接拷贝 template/ 目录
cd my-charger
npx wrangler login
npx wrangler d1 create my-charger         # 把输出的 database_id 填进 wrangler.jsonc
npx wrangler d1 execute my-charger --remote --file schema.sql
npx wrangler deploy
```

`template/worker.example.js` 是骨架，你需要填三处 TODO：接口地址、请求参数、状态码对照表。几个经验：

- **并行查询**：几台主控器用 `Promise.allSettled` 同时查，一台失败不影响其他。
- **只写变化**：状态和上一次一样就不写库。免费版 D1 每天有读写额度，每分钟全量写很快会用完。
- **租约**：除了定时任务，页面被访问时如果发现数据过期也顺手巡查一次；两者用数据库里的一把“租约”防止重复。
- **原始快照单独存一份**：每分钟一行，把所有主控器的状态字符串拼起来存。以后规则改了（比如发现某个状态码含义理解错了），
  可以拿原始快照重新归类，不至于数据作废。

## 4. 从“快照”到“充电记录”

平台只告诉你“现在”每个口的状态，“一次充电”是我们自己拼出来的：

| 上一次 | 这一次 | 含义 |
|---|---|---|
| 空闲 | 充电中 / 浮充 | 开始了一次充电 → 新建一条记录 |
| 充电中 | 浮充 | 还是同一次（快充满了） |
| 充电中 / 浮充 | 空闲 | 充完离开 → 记录结束时间 |
| 空闲 | 故障 | 状态切换，不算充电 |

因为每分钟才看一次，**真实开始时间只知道落在“上一次看到它空闲”和“这一次看到它在充”之间**。
所以数据库里开始、结束都存成区间（见 `template/schema.sql` 的 `start_lo` / `end_lo`），算时长时取中点，误差也能算出来。

详细的统计口径见 [数据与统计.md](数据与统计.md)。

## 5. 画页面：按真实布局渲染

前端只是一个 `index.html`（不需要构建工具），每 30 秒请求一次 `/api/status`：

1. 把第 1 步的草图写成一个布局配置，例如：
   ```js
   const LAYOUT = [
     { label: "Y7", row: 0, col: 1, dir: "ltr", facing: "up" },   // 一排 12 个口，从左到右，车头朝上
     { label: "Y6", row: 1, col: 1, dir: "rtl", facing: "down" },
     // ...
   ];
   ```
2. 每个口画一个格子 + 一辆小车，颜色对应状态。
3. 充电中的格子可以按“已充时间 ÷ 平台单次最长时长”从下往上灌绿色，一眼看出哪个口快空出来了。
4. 手机屏幕放不下整张图：改成“位置小地图 + 每台主控器一张卡片”，小地图可以左右滑动。

## 6. 注意夜间断电之类的“现场规则”

玉湖的充电桩 0:00–6:00 统一断电，0 点所有订单被强制结束。这类规则会影响：

- **统计**：0 点结束的充电时长是被截断的，不能直接当“充满需要多久”；
- **巡查频率**：夜里所有口都空着又没有变化时，可以降为 30 分钟查一次，6:00 恢复；
- **页面提示**：夜里打开页面时提醒一下“现在断电中”。

你所在的车棚可能有不同的规则，多观察几天再定。

## 7. 上线之后

- 平台的接口随时可能变化，挂了就重新抓一次包对照。
- 欢迎把你的版本也发出来，互相交流 🙌
